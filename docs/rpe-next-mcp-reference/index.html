A conversion proposal, not an installed server

Documentation only. No rpe-next MCP server has been implemented, no editor connection is made, and no chart is modified. The inventory is a faithful mapping, not a recommendation to add 50 tools to PhiChain.

Based on rpe-next v0.13.0, commit 274bc55, inspected on 2026-10-27. All 53 native Agent command definitions were collected by registering their definitions without executing their handlers. Descriptions and native schemas are preserved in native-tools.json.

Proposed connection: external Agent → MCP stdio adapter → authenticated local editor bridge → existing command registry → live editor session. The editor remains the source of truth. Its built-in chat/model loop would not be needed to author via MCP. Native manual tools remain available.

Setup would require implementing the stdio adapter, an editor-side transport, and result/approval/cancellation adapters. There is no working launch command or existing endpoint to configure yet. Browser connections would also need a local relay or another explicit transport; desktop bridging is a separate implementation choice.

How the agent actually writes a chart

  1. editor_context: identify session, revision, selected line/notes and timing bases.
  2. chart_read / chart_query: resolve exact source indices, read affected notes, native event tracks, parents and other dependencies. Retrieve chart_templates when creating objects.
  3. Choose the smallest complete representation: chart_patch for fields, chart_transform for repeated numeric changes, chart_generate for template sequences, or chart_script for arbitrary algorithms and multi-array edits. Native generators are available when they match the task.
  4. The native handler prepares a candidate chart. Host validation and permission checks run; session/chart validity is checked again before one native commit. A successful chart batch is one undo entry.
  5. Read the changed data, run diagnose, navigate to relevant times and inspect actual preview_capture images. Correct through another fresh guarded operation.
  6. Use project_save when requested. Ordinary chart edits remain in memory until normal save/autosave.

Scripts can express moving notes between line arrays, editing several tracks together, or computing a whole motion sequence in one request. They do not automatically solve parent transforms, maintain judgment positions, or know what looks good. Those decisions still belong to the agent.

Example: mirror exactly three existing notes

Read line 0’s notes and relevant context; use original source indices [0,1,2] with chart_transform and {"/positionX":"-positionX"}. Only those fields change, with one undo entry. This mirrors local x; world-space symmetry under transformed parents requires additional math.

Example: move existing notes to another line

Use chart_script to remove chosen items from one array and append them to another within the same candidate chart. No intermediate live deletion is exposed. Review a dry run, then execute with fresh guards. The example below preserves JSON fields, not screen-space trajectory or a guaranteed stable note identity.

chart_script

Run JavaScript in a dedicated Worker with direct read/write access to a full chart copy, supporting arbitrary algorithms, loops, filtering, and note/event/judge line/noise area/mod data operations. chart is a mutable copy and input is custom data. api.createNote(type,beat,positionX,endBeat=beat+1); only Hold (type=2) uses endBeat, others have identical start and end; api.createEvent(start,end,startBeat,endBeat); api.createLine(name?); api.createNoiseArea(startBeat,endBeat); api.createNoiseEvent(start,end,startBeat,endBeat,anchor?). These constructors take beat parameters as decimal numbers; to write the time field directly, use api.fromNumber(number) to generate a beat array. Also available: api.beatValue(array), parseBeat(text), easing(progress,id), clone(value), report(value). By default the modified chart is used; return {chart,result} to return a different chart and brief statistics. No DOM, network, credentials, or local file access; the host validates and commits once, and the change can be undone. Whole-line deletion/reordering and bulk deletion are approved as risky operations; dryRun only previews the plan.

This is the most general write path: a Worker edits a copy of the complete chart; the host validates and commits once. No DOM, network, Node, credentials or workspace APIs. Default 10 s; allowed 100–30,000 ms. dryRun computes without committing. The move example assumes two existing lines and preserves note JSON fields; moving across differently transformed lines does not preserve screen-space motion automatically. Re-run with fresh guards and dryRun=false only after reviewing the plan. This is not a reusable prepared-plan token.

The material difference is the vocabulary of writes: field patches, host-evaluated expressions and validated scripts reduce repetitive model-generated data. MCP is the transport in both designs. This page does not claim that the wider write vocabulary guarantees better chart quality.

Units, targeting and recovery

  • Native indices are zero-based. A user's “notes 1–41” means exactly 41 playable objects under an explicitly chosen ordering. Notes on one line in source array order can be read with offset=0, limit=41; chart-wide ordinal order requires explicitly gathering and ordering playable notes across lines. Do not substitute beats 1–41.
  • Raw RPE JSON stores beats as [whole,numerator,denominator]. Several command parameters also accept numeric/string beats; inspect the native parameter description. Native schemas leave some beat values untyped. This proposal preserves that weakness rather than silently tightening accepted syntax.
  • Line-local beats include the line bpmfactor; noise-area timing uses global beats. Music seconds and chart seconds differ by META.offset / 1000. Navigation and context distinguish these bases.
  • chart_query time overlap is not full visual lifetime. Early visibility, preceding speed events, parent motion and hold tails require further reads and render inspection.
  • Native revision identity changes with immutable chart objects; it is not a persistent chart ID. JSON paths/indices must be re-resolved after structural edits. Do not reuse indices merely because a tool succeeded.
  • General chart writes validate before a single native commit. editor_api and file/material operations do not promise equivalent transaction rollback or ordinary undo.
  • Native permissions can escalate based on the prepared plan: line deletion/reordering, large deletions and asset changes may be dangerous. The exported access label is the registration default, not a complete per-call classification. history, global_events and other mixed-action commands must not be blindly marked readOnlyHint=true.
  • chart_patch supports up to 2,000 operations; chart_transform up to 10,000 explicit indices; chart_generate count up to 10,000. Read/query pages cap at 200. Transport byte limits would still need to be chosen for the new bridge.
  • dryRun is supported by chart_script; analyzeOnly by fitting tools. There is no uniform native dry-run switch across every chart write. Approval prepares a candidate internally, but is not itself a public dry-run MCP call.
  • On stale state, reread and recompute. After transport loss, inspect current chart/history before retrying: execution may have completed. Stop/cancel does not roll back earlier successful operations. A new MCP adapter must implement these transport semantics explicitly.
  • diagnose checks native chart structure and known issues; it is not an aesthetic, human-playability, or full render-correctness proof.
